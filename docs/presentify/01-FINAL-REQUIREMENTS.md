## 4. Main workflows

**Admin:** Create Meeting (wizard: details → presenters → sessions & presentations → supporting material → access & downloads → QR → review & publish) → Display QR at the venue.
**Participant:** Scan QR → enter Name / Designation / Organisation (+ configured fields, consent) → view presentation and supporting material → download if permitted. Kannada/English switch at the top.
**After the meeting:** Participants → Attendance → Access/Download activity → Export PDF/Excel/CSV → Archive.

Statuses: **Draft → Published** (shown automatically as *Scheduled / Active / Completed* from the meeting times; admin can end early or extend) **→ Archived**. Replacing a file creates a new version (uploaded by, time, file name, change notes); older versions can be restored by an admin.

## 5. Non-functional requirements

| Area | Requirement |
|---|---|
| Performance | QR landing page < 60 KB, server response < 200 ms at 500 simultaneous participants on the SDC server; meeting data cached in memory and refreshed on change; files streamed, never loaded fully into memory |
| Security | OWASP ASVS Level 2 / OWASP Top 10 controls (see 00-DISCOVERY §6), designed to pass the **CERT-In empanelled security audit** that State Data Centres normally require before go-live |
| Accessibility | WCAG 2.1 AA practices; GIGW (Guidelines for Indian Government Websites) — bilingual, keyboard navigation, high contrast, large text |
| Kannada | Unicode Kannada for all screen text and for data entry (names may be typed in Kannada); Noto Sans Kannada font bundled (no internet needed); PDF reports rendered by a built-in browser engine so Kannada letters join correctly |
| Devices | Android, iPhone, tablets, desktop browsers (current Chrome, Edge, Safari, Firefox); projector display tuned for 1920×1080 |
| Privacy | DPDP Act 2023: consent notice (editable per organisation, English + Kannada), minimum fields, retention, no participant data visible to other participants |
| Honesty | No claims of DRM, offline mode, working backups or e-mail delivery unless implemented and tested |

**Translation note:** I will provide the Kannada text for all screens, but official Kannada wording should be reviewed by a native speaker in your organisation before go-live. All text sits in one file per language, so corrections need no programming.

## 6. Technology (decided)

You asked me to choose for best performance. In plain terms:

| Part | Choice | Why (plain language) |
|---|---|---|
| Programming language | **TypeScript** everywhere | One language for the screens and the server, so rules such as "Name is required" are written once and checked in both places — fewer mistakes. |
| Server | **Node.js 22 LTS + Fastify** | Fastify is one of the fastest web servers available for Node.js. It is very good at handling hundreds of phones at the same moment, because most of that work is waiting for the network and the database, which Node.js handles efficiently. It also produces the API documentation (Swagger) automatically. |
| Participant pages | **Built on the server as plain HTML** | Opens almost instantly even on old phones and weak Wi-Fi; no large app to download. |
| Admin screens | **React** with an accessible component library (Mantine) | Comfortable forms, the meeting wizard, dashboards; works well with keyboards and screen readers. |
| Database | **PostgreSQL 17** | Reliable, free, accepted in government data centres; database-level rules keep organisations apart. |
| Background work | Job queue inside PostgreSQL | Previews, virus scans, report exports and clean-ups run in the background without slowing the screens; no extra software needed. |
| File storage | Local folder (laptop/SDC) with the option to switch to S3-type storage later | No code changes needed to switch. |
| Document viewer | PDF.js (built in) | Views PDFs and converted PowerPoint/Word inside the page with no third-party service. |
| Reports | PDF (built-in browser engine), Excel, CSV | Correct Kannada in PDFs. |
| Packaging | **Docker** | The same package runs on your laptop and in the State Data Centre. A non-Docker installation guide (for SDC servers where Docker is not permitted) is also provided. |

FastAPI (Python) would perform similarly for this kind of application; it was not chosen because it would need two languages and two sets of tools to maintain.

## 7. Environments

### Stage 1 — Your laptop
- Install **Docker Desktop**, then one command starts Presentify (database, server, background worker).
- Recommended: 8 GB RAM or more, 20 GB free disk space.
- **Testing with phones:** laptop and phones on the same Wi-Fi (a mobile hotspot works best; many office Wi-Fi networks block phone-to-laptop connections). The QR points to the laptop's network address.
- **Laptop mode uses plain HTTP** on the local network, because phones do not trust home-made security certificates. This is acceptable for testing and demonstrations only; it is clearly shown on screen as *"Test mode — not for official use"*, and real personal data should not be collected in this mode.
- Virus scanning off (saves memory); can be switched on.

### Stage 2 — State Data Centre
- HTTPS only with a certificate for the official domain (to be provided by SDC/NIC), HSTS, virus scanning on.
- Typically a Linux virtual machine (RHEL / Ubuntu); Docker or native installation.
- Security audit readiness checklist and documentation provided.
- Firewall/proxy rules and the server list will be documented for the SDC team.

## 8. Backups (NAS)

- Nightly: encrypted PostgreSQL backup + copy of uploaded files and configuration to a folder on the **network storage drive** (mounted as a network share).
- Retention: 14 daily, 8 weekly, 12 monthly.
- `verify` script checks each backup; `restore` script with step-by-step guide; restore tested before the backup is reported as working.
- Diagnostics page shows *"Last successful backup"* only from real backup records.
- On the laptop, the NAS share path is set in the configuration file (e.g. `\\NAS\presentify-backup` mounted into Docker).
